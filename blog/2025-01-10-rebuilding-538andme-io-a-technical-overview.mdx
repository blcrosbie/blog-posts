## Introduction

After a year of hosting 538andme.io and approximately four years of collecting voting results from both the House and Senate, it's time to pause and rebuild. This post outlines the technical underpinnings of the site, the challenges faced, and the features planned for the next iteration.

## Problem Framing

The initial version of 538andme.io was centered on analyzing voting performance. Key metrics included the frequency of representatives abandoning their duty to vote and their alignment with party decisions. However, several unexpected issues arose, including bugs related to representatives who held their seats until death, leaving seats unfilled for 3-9 months. This not only skewed data but also raised questions about the representational integrity of the system.

## System Model

### Current Architecture

The current architecture primarily relies on a combination of web scraping and a SQL database for storing voting data. The scraping process collects data from various governmental websites, while the SQL database is structured to facilitate querying and analysis. For real-time data processing, Python scripts are utilized, which run on a scheduled basis via a task scheduler.

### Data Collection

The data collection process is designed to be idempotent, ensuring that repeated runs do not lead to duplicate records. This is critical given the fluctuating nature of congressional representation. The system currently tracks:

- Voting frequency
- Party alignment
- Issues supported or rejected

### Challenges Encountered

1. **Data Integrity**: Instances of representatives holding seats posthumously created significant data integrity issues, resulting in misleading visualizations and statistics.
2. **Real-time Updates**: The need for timely updates on representative statuses became apparent, particularly following elections or resignations.
3. **Scalability**: As more features were envisioned, the existing architecture began to show signs of strain, necessitating a more robust solution.

## Trade-offs

### Short-term vs. Long-term Solutions

While quick fixes such as manual updates to the database could temporarily resolve issues, they are not sustainable in the long run. The trade-off is between implementing a more complex automated system now versus maintaining a less efficient manual process that could lead to further inaccuracies.

### Additional Features

For Version 2.0, expected to launch in 1-2 years in preparation for the next voting cycle in November 2026, several features are planned:

- **Enhanced Indexing System**: A better indexing system to parse proposed, drafted, and voted laws in Congress.
- **Real-time Alerts**: Notifications for changes in representative statuses, ensuring that data remains current.
- **Improved Visualization**: Enhanced visual representations of data to better communicate findings.

## Worked Example

### Initial Vote Count Analysis

The first vote count extracted at the inception of this project was on January 7, 2021. This vote aimed to determine the eligibility of Electoral College votes from Pennsylvania towards Joe Biden's victory. 

- **Total Votes Cast**: Approximately 6.9 million
- **Percentage of Mail-in Votes**: About 50%
- **Vote Count Disputed**: 0.5% of total votes were contested.

This case exemplified the intricate connection between voting processes and data integrity, showcasing how political dynamics can directly influence data collection and interpretation.
